## 1. 개요

| 항목 | 내용 |
|---|---|
| 목적 | 2026 팀장 리더십 교육(Great Candor) 후, GC Review 면담을 마친 팀장이 ① 교육 내용을 얼마나 기억하는지 ② 면담에서 얼마나 적용했는지를 스스로 돌아보게 한다 |
| 측정 틀 | Kirkpatrick Level 2(학습: 기억) · Level 3(행동: 적용). Level 1·4는 이 앱에서 측정하지 않음 |
| 대상 | GC녹십자 팀장 170명. 앱은 대상자 명단을 갖지 않으며, 170명은 참여율 분모로 쓰는 관리자 설정값 |
| 운영 | Vercel. 기존 앱(v3.8.9)과 별개 |
| 접근 | 로그인 없음. 안내 메일·메신저 링크에 붙은 입장 키로만 열림 |
| 운영 기간 | 마감일 있음. 마감 후 접속 시 '이번 차수는 마감됐어요' 안내만 표시 |
| 개발 | 기업문화팀이 Claude Code로 개발 → GitHub → Vercel 자동 배포 |

## 2. 기술 구성

| 항목 | 결정 |
|---|---|
| 서버 | Python FastAPI 1개(Vercel Python 런타임, Python 3.12). 함수 리전 `icn1`(서울) |
| DB | Postgres — Vercel Marketplace(Neon 또는 Supabase)로 연결, `DATABASE_URL` 환경 변수. **제공사는 Claude Code가 연결 단계에서 선택**(서울 또는 가장 가까운 리전 우선, 선택 이유를 README에 기록). 로컬은 SQLite. 서버리스 환경이므로 연결 풀러(pooled) 주소 사용 |
| 화면 | `public/index.html`(사용자), `public/admin.html`(관리자) 한 페이지 앱. 빌드 단계 없이 동작(프레임워크는 CDN 방식 허용) |
| 문구 | `/api/content` 가 `content/content.json` 을 내려줌 |
| AI | 사용하지 않음. 결과는 모두 규칙 기반 |
| PDF | 브라우저에서 생성 |
| 화면 폭 | 모바일 UI 하나. 본문 최대 480px 가운데 정렬, 페이지 배경·양옆 여백 흰색(예외: 결과 정리 화면은 전체 검정, 안내·퀵 리뷰 시작·완료 화면은 전체 그라데이션), 테두리·그림자 없음. 높이 100dvh, 상단 바·진행 막대·하단 버튼 고정, 가운데만 스크롤 |
| 관리자 화면 | PC 전용(최소 폭 1280px) |
| 디자인 토큰 | `design/gc-hr-tokens.json`. 예외: 버튼 48px·본문 16px, 별명 토큰·리더명 토큰(3장) |

## 3. 화면 흐름 (사용자 21개)

```
안내 → 리더명 정하기 → 퀵 리뷰 시작 → 핵심 메시지 1~5 → 키워드      [STEP 1, 참여자당 1번]
 → 구성원 떠올리기 → 체크 1~5 → 결과 정리 → 결과 1 경향과 기억
 → 결과 2 잘한 점 → 결과 3 다음에 해 볼 것 → 실천 1개 → 완료      [STEP 2, 구성원마다 반복]
완료 → '다른 구성원으로 점검하기' → 구성원 떠올리기 (횟수 제한 없음)
```

| 화면 | 디자인 파일 | 핵심 규칙 |
|---|---|---|
| (입장 확인) | — | 입장 키가 없거나 틀리면 `notice.entry_denied` 만 표시. 맞으면 브라우저 저장소에 보관해 이후 키 없는 주소로도 열림 |
| 안내 | Notice | 화살표 하나로 다음(리더명)으로. '나중에 할게요'·확인창·종료 화면 없음. '약 {n}분'은 값이 생기기 전까지 숨김. 이어 하기 안내 한 줄 |
| 리더명 정하기 | LeaderName | 3.1 참조. 다음 이동은 안내·퀵 리뷰와 같은 화살표(고르기 전에는 흐리게 멈춤) |
| 퀵 리뷰 시작 | Intro | 상단에 '[리더명]님,' 표시. 화살표 애니메이션(동작 줄이기 설정 시 정지) |
| 핵심 메시지 1~5 | Review, Candor, Review2, Review3, Review4 | 버튼 순서: 기억나지 않아요 → 기억나요. 어느 쪽이든 다음으로 이동. 진행 1/6~5/6 |
| 키워드 | Keyword | 9개 + '잘 떠오르지 않아요'(단독 선택). 1~3개. 0개면 '다음' 막힘. 진행 6/6. 9개의 순서는 리더마다 무작위(2026-11-27 결정, 처음 고른 키워드의 순서 효과 방지), 같은 리더는 브라우저에 저장한 같은 순서. '잘 떠오르지 않아요'는 늘 맨 뒤 |
| 구성원 떠올리기 | Main | 별명(자동 생성/직접, 20자) + 상황 복수 선택('특별한 상황은 없었어요'는 단독). 별명 비어 있거나 상황 0개면 '다음' 막힘 + '이 페이지의 문항에 모두 답해 주세요.' 안내. 하단 개인정보 안내 문구 없음 |
| 체크 1~5 | Checklist ~ Checklist5 | 페이지 문항에 모두 답해야 '다음'(마지막은 '결과 보기'). 4.2 참조 |
| 결과 정리 | Analyzing | **검정 배경(#000000) + 흰 글자**(이 화면만, 바깥 여백까지 검정, 상태 표시줄 색도 검정). 5→1 카운트다운(숫자 하나 0.6초, 총 3초, 흰 숫자 72px, 원 #1f1f1f) → 체크 표시 → 결과 1로 자동 이동. 숫자가 바뀔 때 커졌다 줄어드는 효과(동작 줄이기 설정이면 효과 없이 숫자만). 숫자는 화면 읽기 프로그램에 읽히지 않게. 결과에서 뒤로 가기로 돌아올 때는 이 화면을 건너뜀 |
| 결과 1 경향과 기억 | Result3 | 결과 정리에서 넘어오면 검정 → 흰 화면 페이드인(0.7초, 뒤로 가기로 돌아올 때·동작 줄이기 설정이면 없음). 제목 '[별명]님과 [리더명]님의 면담은 ‘[유형명]’에 가까웠어요'(유형명은 작은따옴표, 줄바꿈은 자연 줄바꿈). 4분면 칸 강조, 기억한 것과 실제로 한 것('판단 근거 보기' 없음). 이모지 애니메이션 없음 |
| 결과 2 잘한 점 | Result | 요약 한 줄 + 행동 최대 3개(2026-11-26 결정). 진입 시 엄지척 👍 애니메이션(3.3, '잘한 점 없음'이면 생략) |
| 결과 3 다음에 해 볼 것 | Result2 | 행동 최대 3개(2026-11-26 결정)(각각 조언) + 꼭 해야 하는 말(추천) → '꼭 해야 하는 말 정하기' |
| 실천 1개 | Action | 제목 '[별명]님과의 다음 면담은 이렇게 시작해보세요.'(2026-11-26 결정). 추천 3개 + '직접 쓸게요'(100자). 직접 쓰기를 골랐는데 비어 있으면 막힘 |
| 완료 | Done | 제목 '[리더명]님, 수고하셨어요'(리더명 토큰으로 이름을 불러 줌). 꽃가루(한 번, 2~3초). 버튼은 한 줄 3칸(같은 크기, 한 번 누르면 바로 실행): 왼쪽부터 다른 구성원 점검하기 / PDF 다운받기(2026-11-26 결정) / 동료에게 추천하기(이름은 두 줄 고정). '결과 다시 보기' 없음. 7장 참조 |

화살표 위치(안내·리더명·퀵 리뷰 공통): 다음으로 가는 화살표(120×64)는 화면 하단 고정 영역에 둔다. 아래에서 16px 여백 + 44px 칸(세 화면 모두 빈 칸) 위에 놓여 세 화면에서 같은 높이에 보인다. 본문은 그 위 영역에서 가운데 정렬(리더명은 위쪽 정렬)하고, 길면 그 영역만 스크롤.

상단 표시: STEP 1 화면은 'STEP 1 · Great Candor Review', STEP 2 화면은 'STEP 2 · 면담 스타일 점검'. 안내·리더명 화면은 'Great Candor Review'. 결과 화면 진행은 결과 1/3~3/3.

### 3.1 리더명 정하기
- 질문: "어떤 리더로 불러 드릴까요?" 보기 4개 + '직접 적을게요'. 문구는 `content.json` → `leader_name`
- 보기 4개는 4분면 유형을 형용사 2개(개인적 케어, 직접적 쓴소리 순)로 표현한 이름이다. 화면에는 유형 이름을 드러내지 않는다

| leader_type | 4분면 | 케어 | 쓴소리 | 보기 문구 |
|---|---|---|---|---|
| rc | 권위 있는 리더 | 높음 | 높음 | 따뜻하고 솔직한 리더 |
| re | 말하지 않는 리더 | 높음 | 낮음 | 다정하고 배려 깊은 리더 |
| oa | 권위주의적 리더 | 낮음 | 높음 | 단호하고 명확한 리더 |
| mi | 방임형 리더 | 낮음 | 낮음 | 차분하고 신중한 리더 |
| custom | — | — | — | 직접 작성(2~15자) |

- 보기 순서는 리더마다 무작위(순서 효과 방지). 처음에는 아무것도 고르지 않은 상태. 고르면 하단에 "앞으로 [리더명]님으로 불러 드려요" 미리보기
- 직접 작성: 앞뒤 공백 제거, 2~15자. 이메일·전화번호·숫자 6자리 이상은 저장 전에 막고 `blocked_message` 표시. "실명, 사번, 직급은 적지 말아 주세요" 상시 표시
- (2026-11-27 결정) 사람 이름처럼 보이면(띄어쓰기 없는 한글 3글자 + 첫 글자가 흔한 성 + 끝 글자가 '는·한·운·인…' 같은 꾸미는 말 끝이 아님) 입력란 아래에 안내만 한다(막지 않음, 오탐 가능). 규칙 데이터는 `leader_name.custom.name_like`, 화면(app.js `looksLikeName`)과 서버(`anonymize.looks_like_person_name`)가 같은 규칙. 관리자 3.1 에는 '실명일 수 있음' 표시
- 화살표를 누르면 참여자 생성(5.2). 리더명은 STEP 1 완료 전까지만 바꿀 수 있음(리더명 화면으로 돌아가 다시 고르면 같은 참여자의 리더명을 갱신)
- 같은 기기·브라우저로 다시 들어오면 이 화면을 건너뛰고 멈춘 곳부터 이어 함
- 부르는 규칙: '[리더명]님'. 직접 쓴 이름이 '리더'로 끝나지 않으면 ' 리더'를 붙여 부른다(예: 묻고 듣는 → 묻고 듣는 리더님). 퀵 리뷰 시작·결과 1·완료 화면 공통
- 저장 형태 = 부르는 형태 = 관리자 표시 형태. ' 리더'를 붙인 뒤 저장하고, 같은 리더명 판단(구분 번호 부여)은 앞뒤 공백 제거·연속 공백 1개로 줄인 값으로 비교. '묻고 듣는'과 '묻고 듣는 리더'는 같은 리더명
- 해석 주의: 리더명은 체크 **전에** 고른 지향점이다. 결과 화면의 4분면 판정에는 쓰지 않는다(판정은 4장 규칙만)

### 3.2 표시 토큰
- `[별명]`(구성원): 배경 `#E3F3EA`, 글자 `#00703C`, 굵게, 모서리 6px, 좌우 여백 8px. 크기는 주변 글자를 따름
- `[리더명]`(리더 본인): 배경 `#f0f0f0`, 글자 `#000000`, 굵게, 모서리 6px, 좌우 여백 8px
- 체크 1~5·결과 1~3·실천 제목은 별명으로 시작하는 질문형(문구는 content.json)
- 구성원에게 하는 말(추천 문장) 안에는 별명을 넣지 않고 `○○` 로 둠

### 3.3 결과 화면 이모지 애니메이션 (결과 2만)
| 화면 | 이모지 | 조건 |
|---|---|---|
| 결과 2 잘한 점 | 👍 엄지척 | '했어요'가 1개 이상일 때만(`results.r2.empty` 이면 생략) |

### 3.4 브랜드 배경 (안내, 퀵 리뷰 시작, 완료)
- 배경: Great Candor 교육 포스터와 같은 그라데이션 `linear-gradient(to bottom left, #96C93E, #00B09B)` (오른쪽 위 연두 → 왼쪽 아래 청록). 바깥 여백까지 브라우저 전체에 적용, 상태 표시줄 색(meta theme-color) #96C93E
- 글자·화살표·뒤로 가기 아이콘: 흰색. 13px 이하 글자는 굵게(700)
- 리더명 토큰: 흰 배경 + 검정 굵게. 별명 토큰: 기존(연녹색 배경·녹색 글자)
- 완료 화면의 꼭 해야 하는 말 카드: 흰 배경 + 검정 글자
- 완료 화면 3칸 버튼: 상자 없이 흰 아이콘(28px) + 흰 굵은 글씨. 누르는 영역은 칸 전체(높이 88px), 눌림·키보드 포커스 시 흰색 12% 배경
- 명도 대비: 흰 글자와 #96C93E 대비는 WCAG AA 기준 미달. 시범 운영 때 실외·밝기 낮춤 환경에서 읽힘 확인

### 3.5 하단 주 버튼
- '다음', '결과 보기', '꼭 해야 하는 말 정하기', 실천 '완료' 등 하단 주 버튼(높이 48px, 둥근 24px): 단색 `#00B09B` + 흰 굵은 16px(그라데이션 없음. 흰 글자 대비 2.7:1로 WCAG AA 미달, 사용자 결정으로 채택)
- 막힌 상태: 회색 배경 #e6e6e6 + 글자 #8f8f8f
- 진행 막대, 선택된 답 칩(했어요 등)은 검정 유지

## 4. 결과 규칙

### 4.1 문항 (17개)
`content.json` → `items`. 행동 문항 13개(답: 했어요/못 했어요), 부족 신호 4개(답: 있었어요/없었어요).

| 축 | 실행 문항 | 부족 신호 |
|---|---|---|
| 개인적 케어(care) | c1_3, c2_1, c3_1, c4_2 | s3, s4 (불쾌한 공격성 쪽) |
| 직접적 쓴소리(challenge) | c3_2, c3_3, c3_4, c4_1 | s1, s2 (파괴적 공감 쪽) |
| 축 없음 | c1_1, c1_2, c2_2, c2_3, c4_3 | — |

### 4.2 해당 없음
- 해당 없음 선택지는 두지 않는다(2026-11-25 결정). 17문항 모두 두 답 중 하나로만 답한다
- c4_1 '등급과 함께 목표 대비 근거를 보여 줬다'는 문구를 유지한다(GC Review 면담에서는 등급을 전한다고 보고 결정). 등급을 전하지 않은 면담이면 '못 했어요'로 처리되어 쓴소리 실행률이 낮아질 수 있음 — 문항 분석에서 이 문항의 '못 했어요' 비율이 유독 높으면 이 원인부터 확인
- 따라서 축별 실행률의 분모는 항상 4(실행 문항 수)

### 4.3 축 판정 → 4분면
```
실행률(축) = 했어요 ÷ 4     # 축별 실행 문항 4개
높음  = 실행률 ≥ 0.5  AND  그 축 부족 신호 '있었어요' ≤ 1
낮음  = 그 외 (실행률 < 0.5 또는 부족 신호 2개 모두 '있었어요')
care 높음 + challenge 높음 → rc 권위 있는 리더
care 높음 + challenge 낮음 → re 말하지 않는 리더
care 낮음 + challenge 높음 → oa 권위주의적 리더
care 낮음 + challenge 낮음 → mi 방임형 리더
```
- 기준값 0.5는 첫 차수 응답 분포를 보고 조정 가능하도록 설정값으로 둔다

- (2026-11-27 결정) 실행률은 기준값 이상인데 부족 신호가 2개 이상이라 낮음이 된 축은 결과 1(화면·PDF)에 한 줄 설명:
  '{축} 행동은 {했어요}/4개 했지만, 체크 5에서 고른 순간이 {n}개라 ‘낮음’으로 봤어요…'(`results.r1.signal_low`, 결과 데이터 `r1.signal_low = [{axis, done, total, signals}]`).
  실행률이 모자라 낮음이면 설명하지 않는다. 시뮬레이션: '했어요' 80% 경향에서 7.6%가 이 경우

### 4.4 결과 1 — 기억한 것과 실제로 한 것
- 리더가 STEP 1에서 고른 키워드(최대 3개)마다 연결 문항의 이번 점검 응답을 '했어요/못 했어요'로 표시
- 연결·판정 규칙: `content.json` → `keywords.items[].linked_items`, `rule`
- '잘 떠오르지 않아요'를 골랐으면 "기억에 남은 키워드가 없었어요"만 표시

### 4.5 결과 2 — 잘한 점 (최대 3개(2026-11-26 결정))
1. 높음으로 판정된 축의 실행 문항 중 '했어요'
2. 축 없음 문항 중 '했어요'
3. 낮음으로 판정된 축의 실행 문항 중 '했어요' — 3개가 차도록 보탬(2026-11-26 결정)
- 같은 순위 안에서는 체크 페이지 순서. '했어요'가 3개보다 적으면 있는 만큼만
- 요약 한 줄은 판정 조합에 따라 `results.r2.summary`
- '했어요'가 0개면 `results.r2.empty`
- (2026-11-27 결정) 3순위(낮음 축의 '했어요')로 들어온 행동은 작은 글씨를 '{축}는 ‘낮음’으로 나왔지만 이번에 해낸 행동 · 도구'로 바꿔 결과 1 과 어긋나 보이지 않게 한다(`results.r2.low_axis_cap`, 결과 데이터 `r2.low_axis`). '했어요' 80% 경향에서는 거의 생기지 않음

### 4.6 결과 3 — 다음에 해 볼 것 (늘 3개(2026-11-27 결정, 이전: 최대 3개·있는 만큼))
1. 낮음으로 판정된 축의 실행 문항 중 '못 했어요'
2. 축 없음 문항 중 '못 했어요'
3. 높음으로 판정된 축의 실행 문항 중 '못 했어요'
4. 체크 5에서 '그랬어요'를 고른 부족 신호 — 낮음 축의 신호 먼저(2026-11-27 결정). 화면: 신호의 `next_label` + '체크 5에서 고른 순간'(`results.r3.signal_cap`) + `advice`
5. 이어 가기 — '했어요' 행동 중 결과 2에 나오지 않은 것(2026-11-27 결정). 화면: `next_label` + `results.r3.keep_cap` + `effect`
- 같은 순위 안에서는 체크 페이지 순서. 13개 행동 중 결과 2에 쓰인 3개를 빼도 10개가 남으므로 결과 3 은 언제나 3개
- 시뮬레이션(2026-11-27, 131,072가지 전수): 이전 규칙은 '했어요' 80% 경향에서 45%가 1~2개였음 → 0%
- 안내 한 줄(목록 위): 1~3순위가 없고 4순위가 있으면 `results.r3.empty_signals`, 1~4순위가 모두 없으면 `results.r3.empty`(모두 해냈어요 → 이어 가기)
- 결과 데이터: `r3.items`(3개), `r3.keep`(그중 5순위), `r3.item`(1~4순위의 첫 항목, 없으면 null), `r3.empty`, `r3.empty_signals`. `keep` 이 없는 예전 결과는 목록 전체를 '못 했어요'로 그린다

### 4.7 꼭 해야 하는 말(추천 문장)
- 고른 상황 중 우선순위가 가장 높은 상황의 문장(`situation_phrases`). 우선순위: 울거나 말이 없어졌어요 > 결과에 반발했어요 > 낮은 등급을 전했어요 > 다른 구성원과 비교했어요 > 자기평가와 차이가 컸어요 > 선배나 연차 높은 구성원이에요 > 고성과자였어요
- '특별한 상황은 없었어요'면 결과 3 첫 항목(`r3.item`, 1~4순위)의 `phrase`. 부족 신호(s1~s4)에도 `phrase` 가 있음(2026-11-27 결정. 이전: 1·2순위에서만 골라 '상황 없음' 점검의 30%(했어요 80% 경향)에 추천 문장이 없었음)
- 그것도 없으면(상황 없음 + 행동 모두 했어요 + 부족 신호 없음) 공통 문장 `general_phrases.all_done`(2026-11-27 결정). 그래서 추천 문장은 언제나 있다. 키 형식: `situation:<id>`, `item:<문항·신호 id>`, `general:<id>`
- 실천 화면: 첫 번째 = 결과 3과 같은 추천 문장('결과에서 추천한 말'), 나머지 2개 = 고르지 않은 상황 중 우선순위가 높은 문장(라벨은 `situation_labels_for_action`)
  - (2026-11-27 결정) 상황을 6~7개 골라 남은 상황 문장이 모자라면 결과 3 항목(못 한 행동·부족 신호, 이어 가기 제외)의 말 → 공통 문장으로 채운다. 유형은 `other_preset`, 라벨은 `action.item_option_label`('다음에 해 볼 것 · {행동}')·`action.general_option_label`. 결과 3 이 이어 가기뿐이고 상황 7개를 모두 고른 경우만 보기가 2개
- 완료 화면·PDF: 실천에서 고른 문장. 직접 썼으면 그 문장 그대로

## 5. 저장 데이터

### 5.1 원칙
- **개인정보를 수집하지 않는다.** 이름·사번·이메일·소속·전화번호 입력란이 없고, IP 주소와 User-Agent 원문을 DB에 저장하지 않는다(기기는 모바일/PC 값만)
- 리더는 참여자 ID(서버가 만든 무작위 UUID)와 리더명으로만 기록된다. 참여자 ID는 브라우저 저장소에 보관
- 별명은 서버에 저장하지 않는다. 그 기기 브라우저에만 보관
- 직접 쓴 문장: 브라우저에서 별명을 `○○` 로 바꾼 뒤 전송 → 서버에서 이메일·전화번호·숫자 6자리 이상 패턴 제거 후 저장. AI는 쓰지 않음
  - 구성원 실명은 자동으로 지울 수 없다 → 실천 화면 안내를 처리와 맞게 '구성원 실명은 적지 말아 주세요. 별명은 ○○로 바꿔 저장하고…'로 바꾸고(2026-11-27 결정, 이전 '이름과 별명을 지운 뒤'는 실제보다 넓은 약속이었음), 관리자 '직접 쓴 문장'(2.8)에서 전체 권한이 문장마다 삭제할 수 있게 함. 같은 문장은 모두 지우고 같은 문장을 담은 `action_custom_text` 이벤트도 지움. 점검의 실천 유형('직접 썼다')은 남겨 2.6 집계는 그대로
- 관리자 화면에 리더 개인의 체크 응답·직접 쓴 문장은 리더명과 연결해 보여 주지 않는다. 4분면 경향만 참여자 탭에서 리더명별(점검별)로 보여 준다(2026-11-25 결정)
- 응답 수집 안내: 리뷰·키워드·체크 응답이 저장·집계된다는 안내 문구는 화면에 두지 않는다(2026-11-25 결정). 실천 화면의 '직접 쓴 문장' 안내만 유지
- 데이터 보관 기간: 지정하지 않음(삭제는 관리자 설정에서만)
- 로그: 서버 로그에 요청 본문(응답·문장)을 남기지 않는다. Vercel 플랫폼의 요청 로그(IP 포함)는 앱 DB와 별개이며 플랜별 보존 기간 후 삭제됨

## 6. 이어 하기·마감
- 페이지마다 '다음'을 누를 때 서버 저장
- 이어 하기는 **같은 기기·같은 브라우저**에서만(참여자 ID 기준). 메일 앱 안 브라우저와 메신저 안 브라우저는 서로 다른 브라우저로 취급됨 → 안내 문구에서 한 경로로 들어오도록 알림
- 다른 기기·브라우저로 들어오면 새 참여자로 시작(연결 방법 없음). 이 경우 관리자 집계에서 같은 사람이 2명으로 셀 수 있음 → 참여 인원·참여율은 '추정'으로 표시
- 브라우저 저장소를 쓸 수 없는 환경(일부 시크릿 모드 등): 진행은 가능하되 이어 하기가 안 된다는 안내를 한 번 보여 주고 `error: storage_unavailable` 기록
- 브라우저 저장소 만료(2026-11-27 결정): iOS Safari 등은 한동안 방문하지 않으면 사이트 저장소를 지울 수 있어 이어 하기·별명이 사라진다. 안내 화면 문구를 '같은 기기·브라우저에서 이어 할 수 있어요. 며칠 비워 두면 이어 하기가 끊길 수 있으니 되도록 한 번에…'로 하고, 안내 메일에도 같은 내용(DEPLOY 4-1). 완료 화면은 PDF 받기를 권함(기존)
- 앱 안 브라우저(2026-11-27 결정): 안내 화면에서 앱 안 브라우저로 처음 열었으면(이 브라우저에 기록 없음) '다른 브라우저로 열기' 안내를 보여 준다. 이미 기록이 있으면 옮기면 이어 하기가 끊기므로 안내하지 않는다. 완료 화면에는 'PDF가 저장되지 않을 수 있어요. 받지 못했다면 캡처' 한 줄
- STEP 1은 참여자당 1번. 끝낸 리더는 재접속 시 구성원 떠올리기부터
- STEP 2 도중 이탈 시 멈춘 페이지부터 이어서 진행 + 상단 안내 + '처음부터 다시'(그 구성원 점검 삭제)
- 공용 기기(2026-11-27 결정): 이어 하기로 들어오면 어느 화면이든 상단에 "[리더명]님의 기록으로 이어서 해요" + '다른 리더예요'를 보여 준다. '다른 리더예요'는 확인 뒤 이 브라우저의 참여자 ID·별명·직접 쓴 말만 지우고 안내 화면부터 새로 시작(서버의 앞 리더 기록은 그대로, 그 리더는 이 기기에서 다시 이어 할 수 없음). 이벤트 `leader_switch`
- 마감 후 접속: '이번 차수는 마감됐어요'만 표시
- 마감 시 미완료 점검: 답한 문항까지 문항별 실행률·부족 신호에 포함. 4분면·결과 지표는 완료한 점검만

## 7. 완료 화면 3칸 (다른 구성원 점검하기, PDF 다운받기, 동료에게 추천하기)

| 칸 | 동작 | 공유 창 미지원(주로 PC) | 기록 |
|---|---|---|---|
| 다른 구성원 점검하기 | 다른 구성원으로 새 점검 시작 → 구성원 떠올리기(별명·상황 비운 상태). 횟수 제한 없음 | 같음 | done_button_click(again), another_member_started |
| PDF 다운받기(2026-11-26 결정) | 결과 PDF 를 파일로 내려받음(공유 창을 쓰지 않음). 완료 화면에 들어오면 미리 만들어 둠 | 같음 | done_button_click(pdf), result_pdf_saved |
| 동료에게 추천하기 | 공유 창 없이 첫 화면(안내) 링크만 클립보드에 복사 + '리플렉션 링크가 복사되었어요.' 알림(2026-11-26 결정). 링크 = 운영 주소 + 입장 키 + `ref=recommend`(리더명·별명·결과 미포함). 아이콘은 링크 모양. 복사가 막힌 브라우저는 링크를 보여 주고 직접 복사. 추천 링크로 열면 늘 안내 화면부터(이 브라우저에 리더 기록이 있으면 안내의 화살표에서 이어 하기) | 같음 | done_button_click(recommend), recommend_copied. 추천 링크 첫 방문 visit_from_recommend(기기 ID, 이미 참여한 기기는 세지 않음) |

- 이름 원칙: 결과는 'PDF 다운받기'(내 기기에 파일로), 동료에게는 '추천하기'(링크만)로 달리 써서 동료에게 결과가 간다는 오해를 막는다(2026-11-26 결정)
- 화면 문구에 메신저 이름을 쓰지 않는다. 보낸 앱은 기록하지 않는다
- PDF 내용: 리더명, 별명, 결과 1~3(결과 2 는 최대 3개, 결과 3 은 늘 3개 — 신호·이어 가기 표시 포함), 꼭 해야 하는 말(판단 근거 없음)
- PDF 한 쪽 맞추기: 넘치면 배율 1 → 0.93 → 0.86 → 0.8 → 0.75 로 줄여 다시 그림(2026-11-27 결정, 0.8·0.75 추가). 가장 긴 조합(리더명·별명 최장, 결과 1 설명 2줄, 결과 3개씩, 직접 쓴 100자)도 1쪽. 견본 `docs/pdf-samples/`
- 추천 링크에는 입장 키가 들어 있어 재전달로 대상 밖까지 퍼질 수 있음 → 문제가 생기면 설정에서 입장 키 변경
- 안내 링크가 메일과 사내 메신저로 발송되므로, 두 앱 안 브라우저에서 PDF 다운로드·공유 창·클립보드 복사 동작을 반드시 검수(앱 안 브라우저는 파일 내려받기를 막는 경우가 있음)

1. Claude Code로 개발 → 로컬(SQLite) 확인 → GitHub push
2. 작업 브랜치 = Vercel Preview 배포(시범 운영용 DB 연결). main 병합 = Production 배포(본 운영 DB). 두 환경의 DB와 입장 키를 분리
3. Vercel 프로젝트 설정: 함수 리전 `icn1`, 환경 변수(2장), Production 도메인
4. 앱 버전(`APP_VERSION`)을 화면 하단에 표시하고 Git 태그와 맞춘다
5. 시범 운영: 기업문화팀 내부(Preview) → 본 운영 첫 주 완료 시간 중앙값으로 안내 화면 '약 {n}분' 재확인
6. 안내 발송: 링크 = Production 주소(**Vercel 기본 주소 `*.vercel.app` 사용**, 회사 도메인 연결 없음) + `?k=입장키`. 메일·메신저 두 경로 모두 같은 링크

### 배포 전 확인 사항
- **Vercel 요금제**: Hobby 플랜은 개인·비상업용으로 제한된다. 회사 업무용이면 Pro 이상이 필요한지 Vercel 약관으로 확인하고 결제 주체를 정한다
- **사내 정보보안 검토**: 사외 클라우드(Vercel, DB 제공사)에 교육 응답·직접 쓴 문장을 저장하는 것이 사내 규정에 맞는지. 개인정보는 없지만 사내 교육 콘텐츠와 행동 기록이 사외에 저장됨
- DB 제공사 리전(서울 또는 인접 리전)과 백업 방식
- 입장 키가 링크 전달로 외부에 퍼질 경우 대응: 설정에서 키 변경 → 새 링크 재발송
- 사내 메신저·메일 앱 안 브라우저에서 Vercel 도메인 접속이 막히지 않는지(사내 프록시·방화벽)
